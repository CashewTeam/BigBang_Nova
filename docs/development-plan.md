# Nova Text 开发计划

## 当前状态

项目已经从“迁移脚手架阶段”进入“补能力、补 feature、补兼容性”阶段。

当前已稳定接通的主链路：

- 本地 `cppjieba` 分词与后台预热
- Compose 设置页、搜索页、大爆炸外层浮层壳
- 悬浮球 + 无障碍文本提取 -> BigBang
- 图片调试 / 图片分享 -> OCR 范围选择 -> BigBang
- 悬浮球白名单 OCR -> 无障碍截图 -> 全屏 OCR -> 最近文本块 -> BigBang

当前仍明显未完成的部分：

- OCR 最近文本块命中还需要继续收敛到更稳定的段落级提取
- BigBang 原版 feature 仍缺“炸了又炸”和编辑模式
- 重新识别链路、复杂场景裁切、三方 App 兼容性和性能优化仍未收口

## 目标一：收敛 OCR 主链路

### 已完成

- ML Kit OCR V2 离线接入
- 设置页调试入口和图片分享入口的范围选择 OCR
- 白名单 OCR 分流
- 悬浮球白名单 OCR 直接按触点命中最近文本块

### 下一步

- [ ] 把“最近文本块”继续收敛为更稳定的段落级提取
- [ ] 明确 OCR 结果的重识别链路
  - 保持当前语言重新识别
  - 切换语言重新识别
  - 手动框选重新识别
- [ ] 优化截图后的场景裁切
  - 网页
  - 长列表
  - 聊天窗口
  - 小窗 / 多窗口
- [ ] 继续打磨 OCR 页交互
  - 加载态
  - 返回路径
  - 范围选择后的默认动作

### 验收

- [ ] 白名单 OCR 命中率和段落准确性明显优于当前版本
- [ ] 重新识别链路在 BigBang 内闭环
- [ ] OCR 失败或取消时无残留页面、无错误回栈

## 目标二：补齐原版 BigBang 核心 feature

### 当前缺口

- “炸了又炸”
- 编辑模式
- 一些原版选择、多选、操作栏细节

### 下一步

- [ ] 实现“炸了又炸”
  - 当前段落识别后
  - 用户上滑或下滑松手
  - 直接提取上一段或下一段文本
  - 如果相邻段落少于 25 个非空白字符，继续向同方向拉取下一段短文本
  - 遇到长段落、没有更多段落，或已累计 3 段短文本时停止，并一次性追加
- [ ] 实现真正可用的编辑模式
  - 不是占位按钮
  - 有明确进入、退出和状态反馈
- [ ] 收口 BigBang 内顶部 / 底部操作栏行为

### 验收

- [ ] “炸了又炸”在真实文本场景下可用
- [ ] 编辑模式不再只是 placeholder
- [ ] BigBang 主交互不再依赖临时兜底

## 目标三：三方应用适配与性能调优

### 下一步

- [ ] 继续排查常见三方 App 的无障碍命中率
- [ ] 继续收敛 OCR 白名单页、截图路径和返回栈问题
- [ ] 优化设置页滚动、BigBang 启动和搜索页打开耗时
- [ ] 建立最小问题清单
  - 问题 App
  - 复现步骤
  - 当前行为
  - 期望行为

### 验收

- [ ] 常见应用中的悬浮球体验基本稳定
- [ ] 设置页 / BigBang / 搜索页无明显掉帧和严重视觉错误
- [ ] 返回栈和浮层关闭逻辑可预测

## 当前不作为主目标

这些事不是永远不做，只是不是下一阶段主目标：

- 全量 Kotlin 化 legacy Java 内核
- 全量 Compose 重写 BigBang 词块布局
- 大规模目录重排
- 引入新的复杂架构层

原因很简单：这些成本高，但不直接补当前最缺的用户能力。

## 执行原则

1. 继续保持“先让主链路可用，再补抽象”。
2. 文档只写当前真实状态，不把目标态写成已完成。
3. 新链路优先复用现有 launcher / dispatcher / settings，不再各起一套分支。
4. 继续保留 legacy Java BigBang 内核，除非有明确收益，否则不重写。
